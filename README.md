# secure-efi-shell

A password-gated build of the EDK2 UEFI shell, backed by a TPM 2.0.

The stock UEFI shell is a Secure Boot bypass waiting to happen: anyone with
physical access can use it to poke at NVRAM, load drivers, or launch arbitrary
signed binaries. This fork prompts for a password before the shell starts and
verifies it against a hash sealed in TPM NV storage behind a
`PolicyPCR(sha256:7)` policy — so the TPM only releases the expected hash when
the machine booted with the expected Secure Boot configuration. Wrong password
three times, or a PCR 7 mismatch (Secure Boot off, different keys), and the
machine cold-resets.

## How the gate works

On entry to `UefiMain`, before any shell functionality is available
(`overlay/ShellPkg/Application/Shell/ShellAuth.c`):

1. Prompt for a password (masked, max 64 chars).
2. Start a TPM policy session, run `TPM2_PolicyPCR` over PCR 7, and read the
   expected 32-byte digest from NV index `0x01800001`. If the policy check
   fails — e.g. Secure Boot state differs from provisioning time — the read is
   refused and the system resets.
3. Stretch the entered password: `SHA256(salt ‖ password)` followed by
   1,000,000 rounds of `SHA256(salt ‖ digest)` (parameters in `ShellAuth.h`,
   mirrored by `gen-digest.py`).
4. Constant-time compare against the TPM value; all sensitive buffers are
   zeroized on every path. Three failures → cold reset.

The overlay also removes the shell's `startup.nsh` PATH-search fallback so a
script planted on some other filesystem can't run automatically.

## Repository layout

| Path | Purpose |
|------|---------|
| `overlay/` | The actual source: files copied over a pinned [tianocore/edk2](https://github.com/tianocore/edk2) checkout (`ShellAuth.c`/`.h`, plus small edits to `Shell.c`, `Shell.inf`, `ShellPkg.dsc`) |
| `flake.nix` | Dev shell, helper scripts, the `secure-efi-shell` package (fetches the released `Shell.efi`), and a NixOS module |
| `gen-digest.py` | Offline KDF — computes the expected digest for TPM provisioning; must stay in sync with `ShellAuth.c` |
| `esp/` | Fake ESP directory booted by QEMU (`Shell.efi` goes in `esp/EFI/BOOT/BOOTX64.EFI`) |
| `edk2/`, `tpmstate/` | Generated by the dev workflow; not tracked |

## Development

Everything runs inside the flake dev shell (`nix develop`, or direnv), which
provides the EDK2 toolchain, QEMU + OVMF (full build, with the TCG2/TPM2
stack), swtpm, tpm2-tools, and these helper commands:

```
setup-edk2         # clone edk2 at the pinned commit, init submodules, apply overlay/
build-shell        # build ShellPkg (X64, GCC) under bear → compile_commands.json
run-qemu           # boot esp/ in QEMU with OVMF + a swtpm TPM2 (state in tpmstate/)
capture-pcr7 HEX   # save the boot-time PCR 7 value (64 hex chars) to tpmstate/pcr7.bin
provision-swtpm    # seal the expected password hash into swtpm's NV, bound to PCR 7
```

Typical loop:

```sh
nix develop
setup-edk2
build-shell
cp edk2/Build/Shell/RELEASE_GCC/X64/ShellPkg/Application/Shell/EA4BB293-2D7F-4456-A681-1F22F42CD0BC/OUTPUT/Shell.efi \
   esp/EFI/BOOT/BOOTX64.EFI
run-qemu                    # first boot: note PCR 7, then quit with Ctrl-A x
capture-pcr7 <pcr7-hex>
provision-swtpm             # prompts for the gate password (QEMU must be off)
run-qemu                    # gate now unlocks with that password
```

`provision-swtpm` recreates NV `0x01800001` with attributes
`ownerwrite|policyread` and a `PolicyPCR(sha256:7)` read policy, then writes
the digest produced by `gen-digest.py`.

## Deploying on NixOS (Limine + sbctl)

The flake exports a NixOS module that adds the released shell to the Limine
boot menu and keeps it signed with the device's own sbctl keys:

```nix
{
  inputs.secure-efi-shell.url = "github:sethechosenone/secure-efi-shell";
  # in your system config:
  imports = [ inputs.secure-efi-shell.nixosModules.secure-efi-shell ];
  boot.secure-efi-shell.enable = true;
}
```

Options: `addBootEntry` (default `true`) adds the Limine menu entry;
`autoSign` (default `true`) re-signs the ESP copy during activation, since the
Limine installer overwrites it with the unsigned binary on every rebuild.

Then provision the real TPM once per device, as root:

```sh
provision-efi-shell   # reads PCR 7 from /dev/tpmrm0, prompts for the password
```

Caveat: with `nixos-rebuild boot` (as opposed to `switch`), activation — and
therefore signing — only runs after the new generation boots. Selecting the
shell entry on that very first reboot finds it unsigned and Secure Boot
rejects it; boot Linux once and it's fixed.

## Threat model and limitations

What the gate is for: stopping a casual-to-moderately-determined attacker with
keyboard access from using the boot-menu shell entry as a Secure Boot-era
escape hatch. It is **not** a defense against an attacker with hardware-level
access or root on the running OS.

What it provides:

- The expected hash never lives on disk in the clear — it sits in TPM NV,
  readable only while PCR 7 matches the provisioned Secure Boot state.
- Fail-closed behavior: a PCR 7 mismatch (Secure Boot off, keys changed) or
  three wrong passwords cold-resets the machine instead of degrading.
- Constant-time comparison and zeroization of password/hash buffers.

Known limitations:

- **SPI flash / firmware attacks.** The root of trust is the platform
  firmware, which lives in SPI flash. An attacker who can reprogram the flash
  (chip clip, or software flash on a machine without protected ranges) can
  replace the firmware with one that extends the *expected* values into PCR 7
  without enforcing Secure Boot — the TPM only knows what the firmware tells
  it. Sealing to PCR 7 is only as strong as the platform's firmware
  protections (Intel Boot Guard / AMD PSB, BIOS write-protect, vendor-locked
  flash). PCR 0 (firmware code) is deliberately *not* in the policy — it would
  brick the gate on every firmware update — so firmware swaps that keep PCR 7
  honest-looking are out of scope.
- **TPM bus interposing.** On a discrete TPM the NV read travels over the
  LPC/SPI bus in the clear: the policy session is unsalted and does not use
  parameter encryption, so a bus sniffer captures the expected digest directly
  and can brute-force the password offline. An active interposer can also
  spoof PCR state outright.
- **Anything else running in the same boot state can read the hash.** The NV
  read policy is `PolicyPCR(7)` and nothing more. Any other code that executes
  while PCR 7 holds the provisioned value — another signed EFI binary, or the
  booted OS itself (root can open a policy session against `/dev/tpmrm0`) —
  can read the digest and mount the same offline attack. The gate's secrecy
  ultimately rests on the password's strength, not on the digest staying
  secret.
- **Offline guessing is bounded by the KDF, not the TPM.** The stretch is 1M
  rounds of SHA-256 — slow-ish, but not memory-hard, and the salt is
  compiled into the binary and shared across installs. TPM anti-hammering
  does not apply (the TPM releases the digest to *any* reader satisfying the
  policy; it never sees the password). A GPU rig makes short work of weak
  passwords; pick a long one.
- **No cross-boot rate limiting.** Three attempts per boot, but rebooting
  resets the counter, so online guessing is limited only by reboot + stretch
  time (a few seconds per attempt).
- **The gate only guards this binary.** If any other shell (e.g. a
  Microsoft-signed one, if the MS UEFI CA is enrolled in `db`) or permissive
  boot path verifies on the machine, the attacker just boots that instead.
  The gate assumes an otherwise locked-down platform: custom `db` only,
  firmware setup password, boot order locked.
- **Console input is unauthenticated.** A hardware keylogger between keyboard
  and machine captures the password; classic evil-maid hardware is out of
  scope.

Operational notes:

- Changing Secure Boot keys or toggling Secure Boot changes PCR 7 and locks
  the gate. Re-run provisioning after any such change.
- The binary must be signed (e.g. with sbctl) to be useful under Secure Boot;
  the NixOS module handles this automatically.
